Authentication Settings

English | Japanese

This document gives an overview of authentication in Gfarm.

Authentication methods

The following authentication methods are available.
sharedsecret
Shared secret authentication. Communication is not encrypted.
tls_sharedsecret
Shared secret authentication over a TLS-encrypted channel.
tls_client_certificate
Client certificate authentication over a TLS-encrypted channel.
sasl
SASL authentication over a TLS-encrypted channel.
With SASL authentication, servers such as gfmd and gfsd cannot be the initiator of a connection. Thus, an authentication method other than sasl and sasl_auth must be configured for authentication between servers.
sasl_auth
SASL authentication over a TLS-encrypted channel. After the authentication is completed, communication is not encrypted.
kerberos
Kerberos authentication with encrypted communication.
kerberos_auth
Kerberos authentication. After the authentication is completed, communication is not encrypted.
gsi
Client certificate authentication over a channel encrypted by GSI (Grid Security Infrastructure).
gsi_auth
GSI authentication. After the authentication is completed, communication is not encrypted.

The following table summarizes the authentication methods.
Name Mnemonic Encryption Mutual authentication Authentication between servers Document
sharedsecret s no no yes auth-sharedsecret.html
tls_sharedsecret S yes yes (*1) yes auth-tls.html
tls_client_certificate T yes yes yes auth-tls.html
sasl_auth a no yes (*1) no auth-sasl.html
sasl A yes yes (*1) no auth-sasl.html
kerberos_auth k no yes yes -
kerberos K yes yes yes -
gsi_auth g no yes partially (*2) auth-gsi.html
gsi G yes yes partially (*2) auth-gsi.html

The mnemonic is the character that indicates the authentication method in the second column of the output of the "gfhost -l" command. Uppercase letters are assigned to encrypted communication, and lowercase letters to unencrypted communication.

Unencrypted communication is vulnerable to attacks such as eavesdropping and TCP connection hijacking. Thus, authentication methods with encrypted communication are recommended for use over a wide area network. Unencrypted communication is provided for higher performance within a site. However, since recent CPUs have instruction sets for encryption, encrypted communication does not necessarily degrade the performance significantly.

Gfarm servers accept connections only from authenticated clients (except the UDP communication that obtains the load average of gfsd for health checks, which works without authentication). Whether the client also authenticates the server, that is, authentication in the reverse direction, depends on the authentication method. This is shown in the "Mutual authentication" column of the table. Without mutual authentication, the client is vulnerable to attacks that impersonate the server, such as DNS spoofing, BGP route hijacking, and ARP spoofing. Thus, authentication methods with mutual authentication are recommended, especially over a wide area network.

The "Authentication between servers" column shows whether the authentication method can be used for authentication between servers such as gfmd and gfsd.

(*1) With these authentication methods, the method indicated by the name is used for authentication of the client by the server. The server is authenticated by the client with the TLS certificate of the server.

(*2) It is known that GSI authentication between servers does not work at least on Ubuntu 22.04. It works on CentOS 8 variants.

Configuring authentication methods

Initial setting

The -a option of config-gfarm at the initial setup adds authentication settings such as the following to gfmd.conf and gfarm2.conf. 
auth enable sharedsecret *
This is an example of "-a sharedsecret", which uses sharedsecret as the authentication method for all hosts. The -a option can be specified multiple times. If the -a option is not specified, all available authentication methods are enabled.

The first parameter of the auth directive is either enable or disable.

The second parameter of the auth directive is an authentication method or "*". "*" means all authentication methods.

The third parameter of the auth directive is the host name or the IP address of the target hosts in one of the following forms.
Host specification Example Meaning
* * all hosts
host name host1.example.net the specified host
.domain name .example.net hosts in the specified domain
IPv4 address 192.168.0.1 the host with the specified IP address
IPv4 address/netmask 192.168.0.0/24 hosts in the specified IP address range

For the same authentication method, the order of auth directives is significant, and they are applied from the top. Thus, the following example 

auth enable * 192.168.0.0/24
auth disable * .blacklist.example.net
auth enable tls_client_certificate *
means
  • all authentication methods are allowed for 192.168.0.0/24
  • no authentication is allowed for hosts in the blacklist.example.net domain
  • tls_client_certificate is used for all other hosts
whereas the following example 
auth enable tls_client_certificate *
auth disable * .blacklist.example.net
auth enable * 192.168.0.0/24
means
  • only tls_client_certificate is allowed for all hosts

The order between different authentication methods is not significant. The client tries the enabled authentication methods in the following order.

  1. sharedsecret
  2. sasl_auth
  3. sasl
  4. tls_sharedsecret
  5. tls_client_certificate
  6. kerberos_auth
  7. kerberos
  8. gsi_auth
  9. gsi
This order can be changed by the auth_trial_order directive.
For example, with the following setting, only tls_client_certificate and sasl are tried in this order, and the other authentication methods are not used. 
auth_trial_order tls_client_certificate sasl

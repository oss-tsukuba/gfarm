Master-Slave Metadata Servers - Tutorial

English | Japanese

This document describes how to configure master-slave metadata servers. See also the setup manual, which describes the setup procedure including TLS authentication.

1. Installation

Let host-a be a master gfmd and host-b be a slave gfmd. Install the Gfarm file system on both host-a and host-b. See the installation manual for details.

2. Configuration

2.1 Master metadata server

Create the user '_gfarmmd', whose privilege is used for inter-gfmd communication. 

# useradd -c "Gfarm gfmd" -m _gfarmmd

Configure the master metadata server as the root user. To enable replicated metadata servers, add the -r option to the config-gfarm command described in the setup manual. 

# config-gfarm -r
The metadata journal file is stored in /var/gfarm-metadata/journal directory by default. The location can be changed by the -j option. If there is an existing metadata server configuration, use config-gfarm-update with the -r option to update the configuration after stopping gfmd. The backend PostgreSQL must be running when config-gfarm-update is executed. 

# systemctl stop gfmd
# config-gfarm-update -r --update
# systemctl start gfmd
Replicated metadata servers require the PostgreSQL backend database.

Register host-b as a slave metadata server.
The gfmdhost command has to be invoked by a Gfarm system administrator, who has the gfarmadm group privilege. By default, the Gfarm system administrator is the user specified by the -A option of the config-gfarm command. 

$ gfmdhost -c host-b
$ gfmdhost -l
+ master -     m (default)    host-a 601
- slave  sync  c (default)    host-b 601
Add a metadb_server_list directive that lists the hostnames and ports of all metadata servers to gfarm2.conf. 

metadb_server_list host-a:601 host-b:601
Dump the metadata as the root user.
If you specified the --prefix or -l option to the config-gfarm command, you have to specify the same options to the gfdump.postgresql command too. 

# gfdump.postgresql -d -f gfarm-pgsql.dmp

Create the shared secret key for a user '_gfarmmd' which is used for inter-gfmd communication. 

# su _gfarmmd
$ gfkey -f -p 31536000
Inter-gfmd communication is authenticated as the _gfarmmd user by the authentication methods enabled in gfmd.conf. The shared secret key is required for sharedsecret and tls_sharedsecret authentication. To specify the authentication methods to try, add the auth_trial_order directive to gfmd.conf on all metadata servers.

2.2 Slave metadata server

Create a user '_gfarmmd' and copy the shared secret key from the master metadata server for inter-gfmd communication. 

# useradd -c "Gfarm gfmd" -m _gfarmmd
copy the shared secret key (~_gfarmmd/.gfarm_shared_key) from host-a
Configure a slave metadata server as the root user. To enable replicated metadata servers, execute config-gfarm with the -r option. 

# config-gfarm -r
Restore the metadata as the root user.
If you specified the --prefix or -l option to the config-gfarm command, you have to specify the same options to the gfdump.postgresql command too. 

# gfdump.postgresql -r -f gfarm-pgsql.dmp

NOTE: Currently, you cannot do "config-gfarm -r" on multiple slave metadata servers simultaneously, even if you'd like to configure multiple slave gfmd at once. Instead, you have to do "config-gfarm -r" and then "gfdump.postgresql -r" on each slave server, and then you can proceed to the next server. Copy gfarm2.conf, to which the metadb_server_list directive was added, from the master metadata server. This is because some gfarm client commands like gfmdhost may be invoked on slave metadata servers as well.

2.3 gfsd and client

Copy gfarm2.conf, to which the metadb_server_list directive was added, from the master metadata server.

See the setup manual for further configuration.

If gfsd is already configured, restart gfsd as the root user.

on each gfsd host: 
# systemctl restart gfsd

Now, master-slave metadata servers are set up.

2.4 Confirmation

gfmdhost -l displays the status of metadata servers. '+' means the slave metadata server is connected to the master metadata server. 

$ gfmdhost -l
+ master -     m (default)    host-a 601
+ slave  sync  c (default)    host-b 601

gfjournal displays the metadata journal. Check whether the metadata updates are successfully transferred to the slave metadata server. 

# gfjournal /var/gfarm-metadata/journal/0000000000.gmj
records  seqnum(min/max)            record length(min/max/ave)
     11            63/          73          24/    118/     43

Update the metadata, for example, by 'gfmkdir tmp'. If the maximum 'seqnum' on the master metadata server is the same as that on the slave metadata server, the updates have been transferred.

3. Upgrade a slave gfmd to a master gfmd

This section explains how to upgrade a slave gfmd to a master gfmd when the master gfmd fails.

Confirm that the master gfmd has been stopped. If it is still running, stop it as the root user on host-a.

host-a: 
# systemctl stop gfmd

Note that one of the following conditions should be met when a slave gfmd is upgraded to a master gfmd.

  • The current master gfmd has been stopped.
  • The current master gfmd cannot communicate with any slave gfmd, gfsd, or client.
If neither of the above conditions is met, the metadata of the master gfmd and slave gfmds may become inconsistent.

To upgrade, send the USR1 signal to the slave gfmd on host-b.

host-b: 
# kill -USR1 <process id of gfmd>
By the way, there is a gfarm_zabbix package which has a feature to automatically upgrade a slave gfmd to a master gfmd, when a fault is detected on a master gfmd.

4. Restore the original master gfmd

This section describes how to restart the old master gfmd as a new slave gfmd.

4.1. Restarting gfmd as a slave

Invoke the following command as the root user:

host-a: 
# systemctl start gfmd-slave
On systems without systemd, use "/etc/init.d/gfmd slavestart" instead.

4.2. Confirmation

Check whether gfmd has started correctly as a slave by the gfmdhost -l command: 

$ gfmdhost -l
+ slave  sync  c (default)    host-a 601
+ master -     m (default)    host-b 601

If "+" is displayed, gfmd has started correctly as a slave.

If "x" is displayed, please proceed to "4.3. Manual synchronization".

4.3. Manual synchronization

If "x" is displayed, it means automatic synchronization is impossible, because too many metadata changes were made while host-a was stopped.
In that case, you have to copy the database on host-b to host-a by the following procedure:

Dump the metadata as the root user on host-b: 

# gfdump.postgresql -d -f gfarm-pgsql.dmp


Restore the metadata as the root user on host-a: 

# gfdump.postgresql -r -f gfarm-pgsql.dmp


Then, try again from "4.2 Confirmation".
